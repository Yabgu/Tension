### 1.3 The report line can no longer drift

`build.sh`'s closing `printf` used to hardcode `runtime=stub`. It now reads the
runtime back out of the config the generator just wrote, so the printed flags and
the emitted flags cannot disagree:

```
==> asc flags for a session guest:
    importMemory=true memoryBase=8388608 initialMemory=132 maximumMemory=512 exportTable=true runtime=incremental
```

Generated artefacts (`build/session.asconfig.json`,
`assembly/runtime/layout.ts`) were **regenerated by `build.sh`**, not hand-edited.

## 3. Example transcripts — the plan's real gate

Plan §9's acceptance test: every example's transcript must be byte-identical
under `incremental` to what it produced under `stub`.

```
example                    stub      incremental result
----------------------------------------------------------------------
audio                      1297      1297      IDENTICAL after normalising 11 timestamp(s), 11 temp path(s)
io                         206       206       IDENTICAL (byte-for-byte)
log                        866       866       IDENTICAL after normalising 11 timestamp(s), 11 temp path(s)
res                        1227      1227      IDENTICAL after normalising 4 timestamp(s), 4 temp path(s)

byte-identical=1  identical-after-normalising=3  differs=0  missing=0
RESULT: PASS
```

All four exit 0.

**About the normalisation, because it is the part that could hide a real
difference.** Two token classes are non-deterministic by nature and unrelated to
the runtime: ISO-8601 timestamps in the log lines, and `mktemp` directory names in
the `res` packing output. `compare-runs.sh` compares **raw bytes first** — `io`
passes that, byte for byte — and only normalises what differs, reporting how many
substitutions it made. A difference surviving normalisation is a failure; none
did. The counts are printed precisely so this is auditable rather than a claim.

**Both sides were captured with a constant framework.** This mattered: an earlier
attempt compared a `stub` capture taken before a framework edit against an
`incremental` capture taken after, which would have proven nothing. The capture
script now pins the runtime (`RUNTIME=<rt>`) by taking each example's own build
script, swapping the runtime flag, and running the host with `--no-build` — so
the host-side argument composition still comes from `run-example.mjs` and only the
runtime varies.

### 3.1 The 131/131 nominal result reproduces on Linux

The verification report's headline acceptance check, reproduced exactly:

```
$ asc game.ts -o game.wasm --runtime {stub,incremental} --target release
$ tension-core game.wasm            # no args, no host options

stub         exit=0 bytes=131 sha=0b798afb1c5dfa8e
incremental  exit=0 bytes=131 sha=0b798afb1c5dfa8e
-> IDENTICAL (131/131)
```

**131 bytes on both, and the same first 16 hex digits of SHA-256** — matching the
Windows verification's 131/131, and holding before and after the framework
refresh.

### 3.2 What could not be transcript-verified here

The **six OGRE examples cannot run on this host.** The adapter loads but
`libfreeimage.so.3` needs `libjxrglue.so.0`, and the system jxrlib (Arch 1.4.4)
does not export the `WMPAlloc` symbol that freeimage was built against:

```
Error: --capability .../libtension_ogre.so: could not load adapter:
  libjxrglue.so.0: undefined symbol: WMPAlloc
```

Supplying the missing soname symlink changes the error from "cannot open" to
"undefined symbol", i.e. the library is ABI-incompatible, not merely unfindable.
This predates the migration and is a property of this machine, not of the
runtime. The OGRE examples are therefore covered here by the **build** matrix
(§2 — all six build, five under both runtimes) and their transcripts are for the
deferred Windows run, where OGRE is known to work. §8.

## 4. Tail latency on this Linux build

**Task requirement: compare against the plan's Linux numbers (3.6–4.1 ms in 2 of
3 reps).** Method: `frame2` times every allocation individually — 3,600 frames ×
100 allocations = 360,000 per rep — because the collector runs inline inside the
allocation that crosses the threshold. 10 reps per runtime, **3,600,000 timed
allocations each**. Compiler: the repo's `asc 0.28.20`. Engine: V8 `node v24.21.0`.

### 4.1 Result

| runtime | worst-across-reps | median-of-worsts | reps with a >1 ms stall | stalls >16 ms | final heap |
|---|---|---|---|---|---|
| **`incremental`** | **3.596 ms** | **0.584 ms** | **4 / 10** | **0** | **1 page** |
| `stub` | **4.051 ms** | 0.344 ms | 1 / 10 (but 1 >4 ms) | **0** | 256 pages |

Top stalls, `incremental` (ms descending):
`3.596, 3.592, 3.499, 3.394, 0.584, 0.546, 0.524, 0.473`
Top stalls, `stub`: `4.051, 0.461, 0.377, 0.353, 0.345, 0.344, 0.342, 0.338`

**Against the plan's numbers: the tail reproduces.** The plan's Linux run saw
3.6–4.1 ms in 2 of 3 reps; this build sees 3.4–3.6 ms in 4 of 10. Same magnitude,
comparable-to-lower rate, so this build is not an outlier in either direction.

**Against the 16 ms frame budget: not exceeded.** The worst stall observed was
**4.051 ms, 25 % of a frame.** Per the task's stopping rule, this does not stop:
the budget holds.

**It exceeds 1 ms, and that is noted.** 4 of 10 incremental reps carried a stall
above 1 ms.

### 4.2 The tail is not the collector — `stub` shows it too, and worse

**This is the finding that changes what the number means.** `stub` produced the
single largest stall in the entire run — **4.051 ms** — and `stub` has *no
collector at all*: its allocator bumps a pointer and writes a block header, and
its `__collect` is a two-line no-op. A multi-millisecond pause inside that path
cannot be collection.

Four measurements support reading the tail as host-side interference rather than
anything the migration introduces:

| measurement | worst | stalls >1 ms |
|---|---|---|
| frame loop, `incremental` (3.6M allocations) | 3.596 ms | 4 |
| frame loop, **`stub`** (3.6M allocations) | **4.051 ms** | 1 (and 1 >4 ms) |
| clock calls only, no allocation (1.8M pairs) | 0.351 ms | 0 |
| pure arithmetic, per-iteration clock (1.8M iterations) | 0.335 ms | 0 |
| an instrumented frame-loop variant (6 reps) | 0.292 ms | 0 |

So: the spike needs *allocation* to appear, but appears under **both** runtimes at
similar magnitude, is **not** reproducible on demand (six clean reps of a variant
of the same workload), and the clock and arithmetic paths — which do the same
number of host calls — never spike. The consistent explanation is intermittent
scheduling or page-fault interference on this host, landing inside whichever loop
happens to be running.

**Consequence for the decision:** the migration does not introduce this tail, and
`incremental` is not worse-served by it than `stub` is. What `incremental` does
add is a higher *total* time inside allocations — median 49.3 ms vs `stub`'s
24.0 ms per 360,000 allocations, i.e. ~1.4 % of the simulated minute. That is the
real, attributable cost of reclaiming memory, and it is the number to compare
against, not the tail.

**Not reconciled with the Windows number here** — the verification report measured
0.599 ms worst with zero stalls above 1 ms in 1,800,000 allocations, and the task
assigns reconciling that to the follow-up. The two are consistent with "the tail
is machine-sensitive", which is precisely what the Windows report concluded.

## 5. The `windowHandle` leak (plan §10 R7)

**Fixed, not merely documented.** The fix is small and the safety of it is
established rather than assumed:

- The adapter's `shim_window_handle` (`tension-ogre/src/adapter.cpp:1152`) does
  two `guest_write`s and returns. It **does not retain the pointer**, so the
  scratch block is the caller's to release.
- Both halves are loaded **before** the free, so there is no use-after-free.
- AS has no `try`/`finally`, so each return path frees explicitly.

**Verified in the emitted code, not just the source.** Rebuilding
`examples/ogre/input-camera` — the example that calls this — grew the wasm from
168,615 to **169,347 bytes**, and `windowHandle`'s body now reads:

```wat
call $~lib/memory/heap.alloc
call $...ogre/index/windowHandleRaw
local.set $1
local.get $1
i32.const 0
i32.ne
if
 local.get $0
 call $~lib/memory/heap.free      ;; error path
 i64.const 0
 return
end
local.get $0
i64.load32_u                      ;; lo
...
i64.load32_u                      ;; hi
local.get $0
call $~lib/memory/heap.free       ;; success path, after the loads
...
```

Two free sites, one per path, both after the loads.

**The other `heap.alloc` in the framework was deliberately left alone.**
`runtime/callbacks.ts:42` allocates the `Callbacks` record, which is
**session-scoped by design** — the session holds its address for the session's
lifetime. Freeing it would be a use-after-free, and changing it would be scope the
plan did not ask for.

## 6. A framework-refresh trap worth recording

The examples depend on the framework as `"tension-framework":
"file:../../tension-framework"`. **npm copies a file dependency**; it does not
symlink it. So the examples build against a snapshot in their own
`node_modules/tension-framework`, and an edit to the repo's
`tension-framework/` does **not** reach them until `npm install` runs again.

I found this the right way — by checking the emitted wasm rather than trusting the
source edit. The first build of `input-camera` after the leak fix emitted the
**old** `windowHandle` with no free calls, because the copy was from 2026-10-04.
After `npm install` the same build emitted the fixed body and grew by 732 bytes.

Two consequences:

- **Anyone re-running this verification must refresh the examples first**
  (`npm install` in each), or they will measure a stale framework and could
  wrongly conclude the fix did nothing.
- The four verified examples were **re-captured on both sides** after refreshing,
  which is why §3's comparison is trustworthy. An earlier comparison had
  `stub` captured pre-refresh and `incremental` post-refresh; it was discarded.

## 8. Windows verification is DEFERRED

**This task does not claim Windows verification.** The migration is landed and
verified on **Linux only**.

The reason is operational and was given in the dispatch: `git fetch` over SSH on
`snow.lan` is broken (Git for Windows' bundled `ssh` finds no usable key; Windows
OpenSSH authenticates but `core.sshCommand` did not fix the fetch). Branch sync is
being fixed separately, and Windows confirmation of *this migration* is its own
follow-up task.

What the follow-up needs to establish, and what is ready for it:

1. **All six OGRE examples' transcripts**, `stub` vs `incremental` — the gap this
   host could not close. `tools/runtime-migration/verify-examples.sh` drives it,
   with `RUNTIME=<rt>` to pin the runtime.
2. **The native-Windows tail number** against §4's Linux number, and
   reconciliation with the verification report's 0.599 ms.
3. **The build matrix**, including whether `ogre/bouncing-ball`'s AS105 presents
   the same way there.

The branch reaches Windows by `git bundle` + `scp` (as the verification did), or
by whatever sync fix lands first.

## 9. For the architect

**A1 — `ogre/bouncing-ball` is broken at HEAD and should be its own fix.**
`tension-framework/session.json` declares `initial_pages: 132`; the example needs
133. Raising it changes the arena shape the host and every adapter agree on and may
bump the layout hash, which is a different change from a runtime swap. Not
attempted here. It is worth deciding before the Windows run, so a pre-existing red
is not mistaken for a migration regression.

**A2 — the `res` and `log` transcripts contain a clock and a temp path.** The gate
is byte-identity, and those two fields can never be byte-identical across two
runs on any runtime. `compare-runs.sh` normalises exactly those two classes and
reports the counts. If the architect wants a stricter gate, the examples would
need a deterministic-output mode; that is a change to the examples, not to the
migration.

**A3 — the multi-millisecond tail is unresolved in one direction.** §4.2 shows it
is not the collector, but I could not identify its cause — scheduling and page
faults are the candidates and this host cannot separate them. It is under the
frame budget with a 4× margin, so it does not block, but it should be on the
record as not fully explained rather than closed as "fine".

**A4 — the `lambda` of this migration is the total allocation time, not the
tail.** If a future workload is sensitive to *aggregate* time, ~2× on allocation
(§4.2) is the number to watch, and the GC tunables are the first lever
(`ASC_GC_GRANULARITY` / `ASC_GC_SWEEPFACTOR` / `ASC_GC_IDLEFACTOR` — note the
`SWEEPFACTOR` name, which is not a typo in this document but is one in AS).

## 2. Phase 1 — the park lands (I103)

The lowering's rule was *"if the operand isn't a task it built, `await` is the operand itself —
no park"*. A handle (`rt.frame()`, `rt.stream(session)`, `rt.job(id)`) is a `Task<T>` with a
**stamped record and no body**, so it took that path: `drive()` empty, value `0`, guest loops to
completion in one host pass.

Both shapes have the same declared type, so the compiler cannot tell them apart — only the
object can. `__awaitShellTask` asks at runtime: a stamped record parks through `scheduler::park`,
anything else runs inline as before. Fiber only; the continuation backend suspends in wasm.

### The artifact evidence

| build | `scheduler::park` import |
|---|---|
| `probe/park-frame`, **before** (compiler `40402d3a`) | **0** |
| `probe/park-frame`, **after** | **1** |

Run on the pre-fix artifact, the whole guest printed **nothing** and exited 0 — the silent
zero, reproduced.

### The transcript

```
probe: park     frame=0 resumes=0
iter: root iteration=1
iter: post frame to task 0 at root iteration=1
fiber: task 0 parked on class 9 key 0
fiber: completing class 9 key 0 with 0 → resume
iter: resume [0] at root iteration=1
probe: resume   frame=0 resumes=1
probe: park     frame=1 resumes=1
iter: root iteration=2
iter: post frame to task 0 at root iteration=2
iter: resume [0] at root iteration=2
probe: resume   frame=1 resumes=2
probe: done     resumes=2
```

**One resume per post, same iteration.** `tests/park_frame.rs` asserts exactly that, by parsing
`iteration=` off both lines — a resume in a later pass is polling, and fails.

### The refusal path (kept, as decision 2 requires)

With the clock's answer withheld, the executor still refuses by name:

```
probe: park     frame=0 resumes=0
Error: fiber executor: task 0 parked on class 9 key 0 and no completion arrived
```

That refusal is a feature and it is unchanged.

### A regression the park exposed, and its fix

Settling the handle reaches `__settleFromRecord`, which wrote `this.value = <T>record.payload`
in the class body. `Task<void>` instantiates no `value` field, so **every** build that
instantiates `Task<void>` became a type error — measured on `examples/ai`, which awaits a
`Task<i32>` and still refused to compile:

```
ERROR TS2339: Property 'value' does not exist on type '~lib/task/Task<void>'.
```

Guarding it inline (`if (!isVoid<T>()) this.value = …`) does **not** work: the assignment is
type-checked for the class's own `T` regardless. The write moves into an `@inline` generic
`__copyPayload<T>`, instantiated at the call site, which is inside the guard (`28eb2a77`).

## 3. Phase 2 — the frame clock: it existed, and it was not wired

**Named:** the producer is `host_loop`'s frame add — `tension-core/src/main.rs`, the
`store.data_mut().scheduler.take_frame()` block — reading `scheduler::take_frame`
(`scheduler.rs:413`), which pops `CLASS_FRAME`/key 0. `scheduler::park` (the import) puts the
task there. `host_loop` is called from `main.rs:2863`, only for a guest that exports
`__taskWake` **and** `_game_running`.

**Why the root's park never saw it:** a root that parks *inside* `__start` is driven by
`run_on_fiber` (`main.rs:806`), never by `host_loop`. Its producer closure asked only the staged
completions and answered `None` otherwise → `Outcome::Stranded`.

**The wiring (defect fix, in scope by decision 3):** that same producer now answers the frame
family from the same clock — `HOST_LOOP_SLICE_MS`, one frame per park, the guest genuinely
suspended for the slice. Every other class still falls through to the named refusal.

**Not invented:** no new clock, no new period, no new ABI. The existing constant, the existing
`(class, key)` vocabulary.

## 5. Phase 4 — the user's two programs

**`examples/async-io` — runs, and parks correctly on its declared backend.** Its `promise`
declaration stays. On fiber it makes **zero parks** and hangs: its entry is a **sync**
`_start_game` that calls `run()`, an async helper lowered to a task factory that nothing
dispatches. That is DL54's residue, not the park — the guest never reaches an `await`.
Removing the declaration was tested again and is still wrong.

**`examples/ai/story.ten` — makes zero parks in 240 s.** It loads the model, opens the session,
prints its command list, and then stops — **before any `await`**, so there is no park class and
key to name. Since the guest never reaches its streaming loop, this round **cannot say** whether
its `await signal` path is right; the mechanism it would use is the one proved on the probe.

**The header comment** — *"zero polls, zero yields"*. Status: **true of the engine now, still
unverified for this example**, and therefore not rewritten. Before DL56 the claim was false on
every backend: `await` on a handle yielded, so the streaming loop would have spun. It is now a
real park (proved on the probe and on `async-io` under `promise`), but `examples/ai` never reaches
it here, and rewriting a comment to describe a run nobody performed is the thing this project
keeps getting wrong. There is a follow-up: why the AI guest stops after its command list.

## 7. What the tree contradicted in this brief

- **`findings/2026-11-27-dl55-drain.md` does not exist.** `findings/` is an empty directory; the
  reboot killed the round before the finding was filed. §1's three paragraphs are the record, and
  this report is written from them plus fresh measurement.
- **"The in-flight change works"** was half right. The dispatch works. The std file it landed in
  had an unterminated doc block that swallowed the next function's comment, and the settle it
  reaches could not instantiate `Task<void>` — so it did not compile the user's AI example at all
  until both were fixed.
- **"A sync entry under fiber emits no start section."** Already corrected in DL54 and still
  worth repeating: `examples/io` runs fine. The hang is upstream of the start section — a sync
  entry calling an async helper.
- **The continuation backend's park is correct and unanswerable on the default path** — that is
  not a regression from this round and not something a fiber-side fix can reach.

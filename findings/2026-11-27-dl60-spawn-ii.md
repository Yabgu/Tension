## 1. B1 — `$serveEntry` and `__driveSlot` on every fiber build (I140)

**The mechanism, in the compiler.** `emitStartsTable` emitted `$serveEntry` **only when
`this.workerExported || Map_keys(this.spawnIndexTargets).length > 0`**. A *parameterised*
async function gets no spawn start, so for a program whose only async function takes an
argument the table was empty and the body was suppressed. Meanwhile the call site is
reachable regardless of the table: `__submitTask` → `__executorInit` takes a reference to
`__mainStep__` → `__drainInbox` → `__serveOne` → `__serveSlot` → `__serveCont`, and on this
backend `__serveCont` is `call $serveEntry(index)`.

Two things I got wrong on the way, both now comments at the site:

1. **`fiberShell` is not the right gate.** Its definition is `asyncShellSuspends &&
   fiberBackendActive` — false precisely for the sync entry this fix exists for. My first
   patch was correct and inert. The condition keys on `fiberBackendActive`.
2. **`compileFunction` on an already-emitted function adds it twice**, and Binaryen answers
   with an exception that surfaces as *"the compiler has crashed"*. Measured on
   `schedule-order`, whose fiber build already had `__driveSlot` through std. Both compiles
   are now gated on `module.hasFunction`.

**The artifact**, `async/serve-entry-sync-root.wasm`:

```
exports: __asyncStatus  __driveSlot  __start  _start_game  memory
```

and the run, whose honesty matters more than its length:

```
$ tension-core build/serve-entry-sync-root.wasm
entry
```

The entry runs. The submitted body does not — that is I142 below, and the fixture asserts
what is true rather than what is wanted.

**Declared delta: none — and that took a second commit to earn.** My first version emitted
the pair on *every* fiber build; Tension's eight `fixtures/fiber/*.wasm` moved with it and,
worse, five of this repo's CI jobs went red on `[fixture mismatch]` across `interop/*`,
`features/*`, `bindings/*` — the default backend is fiber, so "every fiber build" is "every
build". The refinement (TensionScript `8ebfa18f`) gates on the **events**:

- `$serveEntry` — `builtin_async_serveCont` sets `compiler.fiberServeEntryNeeded`; the tail
  emits the body when it is set. The call and its target are one decision.
- `__driveSlot` — exported when `~lib/thread/__submitTask` is in the module. A guest that
  cannot submit has nothing to drain, and the host already reads the export's absence as
  "nothing to drain".

With that, the eight fiber fixtures are **byte-identical to `ce77d39`** and the compiler
repo's own suite reports **zero `fixture mismatch`**. Two wrong oracles on the way, both now
comments at the site: `hasFunction(SERVE_ENTRY)` is true for a *dangling* call (Binaryen
holds a placeholder), so adding a body under that name is a duplicate and surfaces as "the
compiler has crashed"; and `elementsByName` says "yes" for every program that links std's
thread machinery, which is not the same question as "can this guest spawn".

## 2. B2 — why the walk never reached the entry file

**DL59's diagnosis was wrong, and the brief repeated it.** The walk *does* reach the entry
file: `afterParse` iterates `program.sources` and skips only `stdSources`, and the entry
`.ten` is in that list. Instrumented, the entry file's statements were compiled and the
rule was consulted for every call in them. What failed was the rule itself, twice:

1. **The shadow guard was inverted.** I compared `this.currentFlow.lookup(name) == null`,
   assuming `lookup` finds locals only. It resolves **globals and functions too**, so for a
   function named `work` it never returned null and the rule never fired. The diagnostic
   that showed it: `DL60CALLEE work lowered=true local=true`. The correct guard is
   `bound != null && bound.kind == ElementKind.FunctionPrototype`.
2. **`Type.auto` is not a valid statement context.** With the guard fixed the rule fired and
   the next error was `Type '~lib/task/Task<void>' is not assignable to type 'auto'`. The
   call has to be compiled against the factory's own return type.

With both corrected, the rule fired and emitted `__submitTask(work(1))` — and that is when
I142 appeared. So B2 is *solved* (the mechanism is named and the rule works); it is not
*landed*, because landing it exposed a defect underneath.

## 3. I142 — the third defect, and why the round stops here

`work$Rec` — the record class the transform synthesizes — reaches the artifact with:

```
work$Rec#constructor
work$Rec#get:$p0   work$Rec#set:$p0
```

and **no `drive`**. The virtual dispatch entry is therefore a bare `unreachable`:

```
(func $~lib/task/TaskBase#drive@override (param $0 i32)
  unreachable)
```

so `__driveSlot` → `task.drive()` traps, and the host reports it exactly right:

```
Error: a spawned task at slot 1 trapped: error while executing backtrace:
    0: ~lib/task/TaskBase#drive@override
    1: ~lib/task-stack/__driveSlot
```

Four hypotheses, each tested and each ruled out by measurement:

- the member is absent from the array — no: `fields=3 idx=1 memberKind=63` (MethodDeclaration);
- `CommonFlags.Override` is required — no: adding it changed nothing;
- a `this` type in the signature is required — **it broke three examples**
  (`scene.ten(992)`, `story.ten(105)`, `game.ts(68)`: `Cannot find name 'this'`), so it is
  the wrong lever;
- the index collides with the constructor — no: a **sibling** method pushed at the same
  index for the experiment did not appear either.

So the cause is in how the compiler emits the members of a class the transform adds after
parsing, not in the declaration the transform writes. That is a compiler round of its own,
and the finding lives at the declaration site in `src/async/stack.ts` so the next round
starts from the evidence rather than the symptom.

**Why the rule was reverted rather than kept as a refusal.** I did land it as a named
refusal first, and the refusal immediately fired on shipped framework code —
`tension-framework/assembly/2d/scene.ten:827`, `drive(canvas, pipe, this, stepper,
maxFrames);` — breaking `2d/box-physics` and dropping the corpus to 21 of 22. A rule that
condemns the framework's own floating-task idiom is not a rule this round can ship. Decision
3 of the brief applies: the rule stays out.

## 5. What the tree contradicted in this brief

- **"B2 — the transform's AST walk never reaches the entry file."** It does. The walk was
  fine; the rule was wrong twice (inverted guard, invalid context type). DL59 inferred a
  walk bug from a rule that never fired; the rule was the bug.
- **"Emit `$serveEntry` for every fiber build"** was correct and necessary but not
  sufficient — it makes the artifact validate, not the work run.
- **Decision 4's gate** ("all N bodies run on both backends") is blocked by I142, which
  neither DL59 nor this brief anticipated. Decisions 5–9 (red control, `schedule-order`
  parity, corpus example, census class) all sit behind it and were not attempted, because a
  red control for a feature that cannot run measures nothing.
- **`--bin` is 311, not 307+**: the four `ready::` tests from DL59 are in it.
- **Deleting `tests/programs/probe/` would have removed committed fixtures** (`park-frame`,
  `input-sources`) — restored by `git checkout` before any further work. The scratch probe
  now lives in `async/` as a registered program instead.

# examples/res — a resource pak, end to end

From this directory (after `npm install`, which fetches the AssemblyScript
compiler):

    npm run build          # asc: assembly/index.ts -> build/game.wasm
    ./pack.sh              # assemble a tree in a temp dir, pack it -> game.tns
    ./run.sh               # tension-core --res game.tns build/game.wasm

`assets/` is an ordinary directory tree (`text/`, `data/`, `textures/`) whose
Files are committed. One File is not: `data/large.bin`, 20 MiB, which `pack.sh`
generates into `build/` (a scratch path) at pack time and copies into a temp
tree alongside the committed assets, which is what gets packed. The committed
`assets/` directory is never written to. The generated bytes are bytes 0..63
repeated — a pure function of the size — so the pak stays byte-reproducible
from source, and `verify.sh` compares the bytes read back out of the pak against
the generated file byte for byte.

A second generated asset, `data/compressed.bin` (2 MiB of zeros), is
*compressible*: the packer stores it as a Deflate stream (PKWARE method 8,
`STREAM FORMAT 2`, `STREAM EXPANDED SIZE`; DESIGN.md §8.4) and the runtime
expands it on open, so the guest reads it at its expanded size. Together the two
generated Files are the two halves of the packer's per-File decision: one stored
and chunked at scale, one compressed. `data/large.bin` stays stored on purpose —
its keystream is incompressible — because it exists to exercise the uncached
chunk path, and a compressible pattern would collapse it and end that coverage.

`game.tns` itself is a build product and is not committed (with the large asset
inside it is ~21 MB); run `pack.sh` before `run.sh`.

`pack.sh` turns the tree into `game.tns`, a Tension Volume whose structure follows the
framing defined in ECMA-208 (DESIGN.md §2), with the directory hierarchy carried
by a content convention (§5.5, §6.7) in a child-index Stream. `run.sh` starts
the interpreter with that pak loaded; the guest reaches every byte through
`tension::res` and never touches the kernel filesystem.

The demo reads `data/large.bin` in spot reads rather than end to end: roughly
10,600 chunks in 2048-byte Buffers is past the runtime's per-open chunk cache
(DESIGN.md §8.3, `MAX_FILE_CHUNKS = 4096`), so the File is read uncached and a
full read would be O(N²) in chain walks. A few seeks — including one that
straddles the first chunk boundary, and one to the last byte — still prove the
multi-chunk path at scale.

`verify.sh` runs the whole loop and adds the checks that matter: the volume is
re-read by an **independent reader** written from the specification
(`verify/verify.py`), which walks File Continuation Header Field Tables (13.13)
for the chunked Files and compares their reassembled bytes against the sources;
packing twice produces identical bytes; and the game's stdout is checked against
what the assets actually contain.

Override the tools with `TENSION_PACK` and `TENSION_CORE`, and the generated
assets' sizes with `TENSION_LARGE_BYTES` (default 20971520) and
`TENSION_COMPRESSIBLE_BYTES` (default 2097152). Note that the packer deflates
every File before it lays the volume out, so a 20 MiB incompressible asset costs
real compression time on each pack (`verify.sh` packs twice).

Development note: the Rust host links a static build of `libtension_res.a`.
After changing anything under `tension-res/`, run `cargo build` in
`tension-core/` before re-running the example, or the demo will use the previous
library. The Zig test suite (`zig build test`) always uses the fresh build and
can be green while the demo is stale.
